# ギャップ補完ナビ — 五段階の手順

<!--

1. 五段階は Website_Architecture.md「零」節の流れをそのまま段階に切った。古典 TRIZ の
   ARIZ は 9 部構成だが、授業の対象者（MOT 受講者・本書の読者）が 1 セッション 30〜60 分で

   完了条件は人が目視で判定できる客観条件（項目の有無・文字数・数値の記入）に限り、
   「良い問題か」のような主観判定は含めない。主観判定は AI の追問に委ね、合否にはしない。
3. 解答保留（solution withholding）は ④ で初めて AI が意見を出す構造で担保する。

4. ヒントの三段階（追問 → 原理を指し示す → 本の事例を示す）は先行研究の graded hints を
   踏襲した。昇格は利用者のクリックのみで起こり、AI が自発的に昇格しない。昇格はイベントとして記録する。
5. 著者が必ず自分で決めるべき点：
   - ① IFR の文型（「〜せずに〜が実現している」）を固定するか自由記述にするか
   - ② 矛盾を 1 組に絞るか、複数組を許すか（現案：主矛盾 1 組 + 副矛盾 任意）
   - ④ 確信度の尺度（0〜100 か 5 段階か）と、AI フィードバックに使う閾値
   - ⑤ 方案書に「本の該当章」を必ず載せるか、任意にするか
   - 各段階の AI 呼び出し回数上限（現案：1 段階あたり 6 回、1 セッション 30 回）

## 全体像

| 段階 | 名称 | 利用者が書くもの | AI の役割 |
| --- | --- | --- | --- |
| ① | 問題と理想の最終結果（IFR） | 困りごと、関係者、現状、IFR | 問いで輪郭をはっきりさせる |
| ② | 矛盾の特定 | 改善パラメーター、悪化パラメーター、矛盾文 | パラメーター表に照らして問う |
| ③ | 発明原理の候補 | 矩阵が示した原理から自分が選んだ原理と理由 | 原理の意味を確認する問いを出す |
| ④ | 自分の案と確信度 | 自案（3 行以上）、確信度 0〜100 | 自案が書かれてから初めて対照・指摘する |
| ⑤ | 方案書 | 方案書の各欄を確認・修正 | 整形と要約のみ。新しい案は加えない |

共通の原則：

- AI は手順の部品である。手順を変えず、段階を飛ばさず、利用者の代わりに決めない。
- AI は**先に問い、後に答える**。利用者の入力に対する確認を一文書いてから、問いを出す。
- AI は完全な方案を出さない。原理を利用者の代わりに選ばない。製品名・会社名を出さない。
- ヒントの昇格は利用者の操作でのみ起こる。AI は「次のヒント段階へ進めます」と案内するにとどめる。
- 各段階の完了条件を満たさないと次へ進めない。条件は画面上に常時表示する。

## ① 問題と理想の最終結果（IFR）

### 目的

「パッケージ製品の標準機能でできること」と「業務が求めること」の隙間を、他人が読んで同じ像を描ける文にする。
解決策を書く段階ではない。ここで案を書き始めた利用者は、AI の問いで問題側に引き戻す。

### 利用者が書くもの

| 欄 | 内容 | 例の形 |
| --- | --- | --- |
| 困りごと | 誰が、どの業務で、何に困っているか | 「経理担当者が月次の原価センタ登録で…」 |
| 現状の対処 | 今どうやって凌いでいるか（手作業・別表・運用ルールなど） | |
| 標準機能の到達点 | パッケージ製品の標準機能がどこまでやってくれるか | |
| 理想の最終結果（IFR） | 「何も追加せずに、〜が実現している」状態 | 「追加開発なしに、申請から登録まで 1 日で終わっている」 |
| 制約 | 変えられないもの（リリース周期、権限、監査要件など） | |

### 完了条件（次へ進める客観条件）

- 困りごと・標準機能の到達点・IFR の 3 欄がすべて埋まっている
- IFR が「〜している」で終わる状態文であり、手段（製品名・技術名）を含まない
- 困りごとに「誰が」「どの業務で」の両方が含まれる

### AI に許されること・禁じられること

| 許される | 禁じられる |
| --- | --- |
| 欄の抜けや曖昧な語を指摘し、問いで埋めさせる | 困りごとを要約して書き換える（利用者が書く） |
| IFR に手段が混じっていれば、それを外した言い方を問う | IFR の文を AI が作る |
| 本の章「コアとともに生きる」等を指して、制約の見落としを問う | 解決策・原理・製品に触れる |

### ヒントの三段階

| 段階 | 内容 | 例 |
| --- | --- | --- |
| 1 追問 | 欄の内容を具体化する問い | 「『遅い』とは、誰が待たされ、何日遅れますか」 |
| 2 原理を指し示す | この段階では原理は示さず、IFR の型（手段を含まない状態文）を指し示す | 「追加開発がゼロだったら、業務はどう見えていますか」 |
| 3 本の事例を示す | 本の主事例（原価センタ）の問題文の形を示し、同じ形で書けるか問う | 「章『主事例：原価センタ』では困りごとを…の順で書いています。あなたの場合は」 |

## ② 矛盾の特定

### 目的

「何かを良くすると、別の何かが悪くなる」を、パラメーター表（`parameters.ja.md`）の語で言い切る。
矛盾が言えないギャップは、たいてい単なる未設定か要件未確定であり、TRIZ の対象ではない。それもこの段階で判る。

### 利用者が書くもの

| 欄 | 内容 |
| --- | --- |
| 改善パラメーター | 表から 1 つ選ぶ（例：P01 業務適合度） |
| 悪化パラメーター | 表から 1 つ選ぶ（例：P02 標準準拠度） |
| 矛盾文 | 「〜を良くするために〜すると、〜が悪くなる」 |
| 副矛盾（任意） | 2 組目以降。主矛盾と区別して記録する |

### 完了条件

- 改善・悪化のパラメーターが表から選ばれており、同一ではない
- 矛盾文に「何をすると」（手段または方向）が含まれる
- 矛盾文の「良くなる」「悪くなる」が、選んだパラメーターの定義と食い違っていない（AI が問うが、最終判断は利用者）

### AI に許されること・禁じられること

| 許される | 禁じられる |
| --- | --- |
| 選ばれたパラメーターの定義を引用し、当てはまるか問う | パラメーターを AI が選ぶ、または「正解は P0x」と言う |
| 「悪化」が実は制約（変えられないもの）ではないかを問う | 矛盾を解消する方向を示唆する |
| 矛盾が「設定不足」「要件未確定」に見える場合、そう問う | 原理番号を口にする |

### ヒントの三段階

| 段階 | 内容 | 例 |
| --- | --- | --- |
| 1 追問 | 選択の根拠を問う | 「P02 を悪化と見た理由は、将来のリリースで壊れるからですか、監査で説明しづらくなるからですか」 |
| 2 原理を指し示す | 原理ではなくパラメーター表の近傍を指し示す | 「P02 と P03 は似ています。どちらが本当に痛いですか」 |
| 3 本の事例を示す | 本の主事例の矛盾（業務適合 × 標準準拠）を示す | 「章『原則：正本はコアにある』の矛盾の書き方を見て、違いを言えますか」 |

## ③ 発明原理の候補

### 目的

矛盾矩阵（`matrix.json`）が返した 2〜4 個の原理を、利用者が**自分の言葉で**自分の問題に当てはめる。
矩阵の出力は候補であり答えではない。候補を捨てて別の原理を選んでもよいが、理由を書く。

### 利用者が書くもの

| 欄 | 内容 |
| --- | --- |
| 矩阵の候補 | 自動表示（編集不可） |
| 選んだ原理 | 1〜3 個。候補外でも可 |
| 当てはめ | 原理ごとに「この原理をこの問題に使うなら、何を何に分ける／出す／挟むのか」を 1〜2 文 |
| 捨てた原理と理由 | 候補のうち採らなかったものの理由（1 文） |

### 完了条件

- 選んだ原理が 1 つ以上あり、それぞれに当てはめの文がある
- 当てはめの文に、自分の問題の固有名詞（業務・部門・データ）が 1 つ以上含まれる（原理の説明の写しではない）
- 候補を全部捨てた場合、代わりの原理と理由がある

### AI に許されること・禁じられること

| 許される | 禁じられる |
| --- | --- |
| 原理の一般的な意味（`principles.ja.md` の 1 行）を引用し、当てはめと合っているか問う | 当てはめ文を AI が書く |
| 当てはめが原理の説明の写しになっていれば、固有名詞で言い直すよう問う | 「この原理が最適」と順位づけする |
| パッケージ製品での対応する打ち手（同ファイルの列）を示し、該当するか問う | 複数原理を組み合わせた案を提示する |

### ヒントの三段階

| 段階 | 内容 | 例 |
| --- | --- | --- |
| 1 追問 | 当てはめの具体化 | 「『分割』で分けるのは業務の手順ですか、データですか、担当者ですか」 |
| 2 原理を指し示す | `principles.ja.md` の「対応する打ち手」列を 1 行だけ示す | 「原理 2『取り出し』のパッケージ製品での打ち手は『ロジックを外に出す』です。あなたの問題で外に出せるものは」 |
| 3 本の事例を示す | その原理が本のどの章でどう使われたかを示す | 「章『MCP：コアをエージェントのツールとして公開する』は原理 2 の例です。何を外に出していますか」 |

## ④ 自分の案と確信度

### 目的

利用者が自分の案を書き、確信度を自己申告してから、AI が初めて対照する。
順序が逆になると「AI の案を利用者が追認する」だけになり、授業の目的（創造的問題解決）から外れる。

### 利用者が書くもの

| 欄 | 内容 |
| --- | --- |
| 自案 | 3 行以上。どの原理を使い、何をどう変えるか、誰が運用するか |
| 残る悪化 | 選んだ悪化パラメーターがどの程度残るか、どう受け入れるか |
| 確信度 | 0〜100。「この案が実務で通ると思う度合い」 |
| 根拠 | 確信度の理由を 1 文 |

### 完了条件

- 自案が 3 行以上あり、使う原理番号を含む
- 確信度が数値で入力されている
- 「残る悪化」欄が埋まっている（「なし」は不可。理由を書く）

確信度が入力されるまで、AI の送信ボタンは無効にする。

### AI に許されること・禁じられること

| 許される | 禁じられる |
| --- | --- |
| 自案を ①〜③ の記述と対照し、矛盾していれば問う | 代替案・改良案を提示する |
| 確信度と根拠の食い違いを問う（高い確信度に薄い根拠、など） | AI 自身の確信度を数値で言って利用者の値を上書きする |
| 判断標準（`criteria.ja.md`）のチェック項目に沿って、未検討の点を問う | 「この案で問題ない」と承認する |
| 本の該当章を指し、同じ論点が扱われていると告げる | 製品・ツール・サービスの固有名を出す |

### ヒントの三段階

| 段階 | 内容 | 例 |
| --- | --- | --- |
| 1 追問 | 案の穴を問う | 「この案で、データの正本はどこに残りますか」 |
| 2 原理を指し示す | 使っていない候補原理を 1 つ指す | 「候補にあった原理 10『先取り作用』は検討しましたか」 |
| 3 本の事例を示す | 本の事例で同じ問題がどう扱われたかを示す（結論は言わない） | 「章『最初の書き込み：意図、チェック、コミット』は同じ論点を扱っています。読んで案を見直しますか」 |

セッション終了時に、AI の見立て（高・中・低の 3 段階）と利用者の確信度を並べて示し、校正差として記録する。
AI の見立ては数値ではなく 3 段階にとどめる（利用者の数値を「正解」で上書きしないため）。

## ⑤ 方案書

### 目的

①〜④ の記述を 1 枚の「ギャップ補完方案書」にまとめ、本の該当章へのリンクを添える。
AI は整形と要約だけを行い、新しい内容を足さない。

### 利用者が書くもの

方案書の欄は自動で埋まる。利用者は各欄を読み、修正し、「次に調べること」を 1 つ以上書く。

| 欄 | 出所 |
| --- | --- |
| 問題と IFR | ① |
| 主矛盾（改善 × 悪化） | ② |
| 使った原理と当てはめ | ③ |
| 自案・残る悪化・確信度 | ④ |
| 本の該当章 | ③ で選んだ原理の `principles.ja.md` の章列 |
| 次に調べること | 利用者が記入 |

### 完了条件

- 「次に調べること」が 1 つ以上ある
- 自動で埋まった欄を利用者が「確認済み」にしている
- 方案書に製品名・会社名・個人名が含まれない（検査は機械的な語彙照合）

### AI に許されること・禁じられること

| 許される | 禁じられる |
| --- | --- |
| ①〜④ の文を要約し、矛盾する記述があれば指摘する | 新しい案・原理・章を加える |
| 「次に調べること」が空なら、④ で問うた未検討点を思い出させる | 方案書の評価（点数・合否）を出す |

### ヒントの三段階

この段階ではヒントの昇格はない。追問のみ。

---

## 回数と記録

- AI 呼び出しは 1 段階 6 回まで、1 セッション 30 回まで。超えたら「この段階は一度ここまで」と告げ、手順書（この文書）へ誘導する。
- 記録するのは段階の出入り、ヒント昇格、確信度、AI 呼び出し（モデル・prompt 版・トークン・遅延）、方案書の出力のみ。利用者の本文は既定で記録しない（`docs/event-schema.md`）。
