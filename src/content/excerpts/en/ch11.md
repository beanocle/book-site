Modern enterprise systems are no longer one platform that does everything.
They are specialized applications connected through interfaces, events, and,
increasingly, AI agents. In that kind of landscape the important question is
not which system does everything, but which system defines the truth.

For most organizations the answer is finance. Whatever happens in purchasing,
manufacturing, sales, or service eventually has to become a financial outcome:
validated, reconciled, and recorded. The system that records it is the final
authority on whether a business event really happened. This book calls that
system the *core*, and uses SAP S/4HANA as its example.

A core like S/4HANA is also a packaged product: someone else built it, and
you adopt it. Around such a product, AI raises two questions that run through
this book — how AI changes the way the product's existing functions are used,
and how gaps should be filled when the product falls short. The channels
described below are the means for both.

This chapter does three things. It explains what makes a core different from
the systems around it. It gives a technical tour of the ways in — every
channel through which a person, a program, or an agent can reach the core —
so that each later chapter can build on a shared picture. And it introduces
the environment in which the book's examples run.

## What a Core System Is

A core system is defined less by what it can do than by what it guarantees.
SAP's finance and controlling modules (FI and CO) guarantee that a posting
balances, that it lands in an open period, that the cost center it names
exists and is valid on that date, and that the user who made it was allowed
to. Those guarantees are why reports can be trusted and why auditors start
there.

The core is also deliberately conservative. In a modern landscape it is not
where most innovation happens. Automation, orchestration, and new user
experiences are built around it — in side-by-side applications that reach it
through well-defined interfaces — while the core stays stable. The division of
labor is simple:

- **The core** ensures consistency and compliance, and records the final
  financial truth.
- **The systems around it** carry the automation, orchestration,
  transformation, and adaptive behavior that changes with the business.

SAP supports this model in two forms. **S/4HANA Cloud Public Edition** is a
standardized, SAP-operated environment that enforces a clean core: extensions
must live outside, and integration goes through released APIs. **S/4HANA
on-premise** (and the Private Edition) allows deeper customization inside the
system, including RFC-enabled function modules, while still supporting
extensions outside it. In both, the space around the core is where new work
happens, and that is the space this book is about.

## Why Understand the Landscape Before Building Agents

Modern platforms make it easy to connect to an API, read business data, and
put an agent in front of it in an afternoon. From a technical point of view
that looks like progress. In an enterprise, connectivity is only the
beginning.

A system like S/4HANA is not a collection of APIs and tables. It is organized
around business processes, authorization models, compliance requirements, and
internal controls built up over decades. Every posting, payment, approval,
and master data change happens inside those controls, and they exist to
protect the integrity of the business, not to slow developers down. The real
question is often not whether something can be automated, but whether it
should be automated in a particular way.

AI sharpens that question, because an agent does not only execute
instructions; it interprets, recommends, and sometimes acts. An agent that
reads accounting data without understanding reporting periods produces
misleading answers. An agent that initiates approvals without understanding
segregation of duties undermines internal control. An agent that executes
transactions without proper authorization becomes an audit finding. In each
case the code may work exactly as designed while the business outcome is
wrong.

So before any agent touches the core, its designers need to know:

- where business data originates,
- which system is the authoritative source for it,
- how users and technical identities are authenticated,
- how permissions are granted and governed,
- how development, test, and production are separated, and
- how business controls are enforced across the landscape.

These are the boundaries within which every channel in this book operates. The
next chapter, Living With the Core, describes them for S/4HANA Cloud.

## A Technical Tour of the Ways In

The introduction sorted the channels into a map by two questions: who acts,
and what contract the core offers. This section explains how each channel
works technically. Each later chapter opens with a deeper introduction to its
own channel; the purpose here is a shared vocabulary.

### The Native User Interface

The baseline channel is a person working in the core's own screens. In S/4HANA
Cloud that means the SAP Fiori launchpad in a browser; in on-premise systems it
also means the classic SAP GUI. Fiori apps are web applications that talk to
the core through OData services, and every check the core applies — field
validation, authorization, posting rules — runs when the user saves.

The contract here is the screen itself: its fields, its messages, and its
checks. It is designed for people, and it changes when SAP improves the
screen. Everything a person can do in the screen is governed, which is why the
native UI is the reference against which every other channel is measured.

### Released Interfaces

A released interface is a programmatic entry point that the vendor publishes
and promises to keep compatible. Two families matter in this book.

**APIs over HTTP.** S/4HANA Cloud exposes released OData services (OData
version 2 and version 4, REST-style APIs over HTTP with typed entities) and
SOAP services. SAP lists them, with their documentation and schemas, in the
SAP Business Accelerator Hub. In the Public Edition an API is not open by
default: an administrator activates it through a *communication arrangement*,
which binds a predefined communication scenario to a communication system (the
caller) and a communication user (the identity the caller uses). Each request
is processed as its own transaction.

**RFC and BAPI.** In on-premise and Private Edition systems, Business APIs
(BAPIs) are released, RFC-enabled function modules. A caller connects with the
SAP NetWeaver RFC SDK — from Python through PyRFC — and calls the BAPI
synchronously. A BAPI that changes data does not commit by itself; the caller
decides with `BAPI_TRANSACTION_COMMIT` or `BAPI_TRANSACTION_ROLLBACK`, which is
what makes check-then-commit and all-or-nothing batches possible.

Both families give a typed, versioned contract and run the core's own business
logic. That is why they are the default for any governed write, and why Part
Two builds the main case on them.

### Events, Data, Files, and Mail

Not every integration is a request waiting for an answer. Some are
asynchronous:

- **Business events.** The core announces that something happened — a cost
  center was changed, a document was posted — and interested systems react.
  The core does not wait for them.
- **Replication.** Master data is copied in bulk from one system to another,
  often through SOAP services built for the purpose. The reference
  implementation's repository keeps, for example, the service definition of a
  bulk cost center replication request.
- **Integration flows.** A middleware such as SAP's Cloud Integration (CPI)
  receives a message, maps it, and calls the target system. The repository
  also contains such a flow for creating a cost center through a BAPI.
- **Files and mail.** Scheduled file transfers over SFTP, and notification
  mail, remain among the most common channels in practice.

The contract here is the message: its format and its delivery guarantees.
These channels are covered in the last chapter of Part Four.

### Vendor Agents

SAP ships AI into its own products. **Joule** is SAP's assistant inside its
applications: a user asks in plain language and Joule explains, finds, or
pre-checks. The **Generative AI Hub** on SAP BTP is a managed gateway through
which applications use large language models from several providers under
enterprise controls. Their behavior and release schedule are defined by SAP.
The chapter Before Agents Touch the Core covers both.

### MCP Tools

The Model Context Protocol (MCP) is an open protocol, introduced by Anthropic
and now hosted by the Agentic AI Foundation under the Linux Foundation, that
standardizes how an AI application connects to external tools and data.
It names three roles. The **host** is the AI application the user works in — a
coding assistant, a desktop chat application, or an agent framework. Inside it,
an **MCP client** connects to one **MCP server**, a program that exposes
capabilities to it. The most important
of these capabilities are **tools**: named operations, each with a
plain-language description and a typed input schema, that the model can decide
to call. Servers can also expose read-only **resources** and reusable
**prompts**. Client and server exchange JSON-RPC messages, either over standard
input and output when the server runs on the same machine, or over
Streamable HTTP.

What makes MCP matter for a core system is where the tool's work happens. A
well-built MCP tool does not touch the core directly; it calls a released
interface, or an application that already enforces the right permissions. MCP
changes *who decides to call* the interface — a model instead of a programmer —
but not *what the core accepts*. Chapter MCP: Exposing the Core as Tools for
Agents builds a server on the reference implementation.

### Skills

A Skill is a package of know-how that an agent loads when it needs it: a
folder with an instruction file describing what the Skill is for and how to do
the task, optionally accompanied by scripts, templates, and reference
material. The agent first sees only each Skill's short description and loads
the full content when a task calls for it, so many Skills can be available
without filling the model's context.

Where a tool is a capability, a Skill is a method: which tool to call first,
which naming rule applies, what to check before submitting. A Skill has no
contract with the core of its own. Its value is that the organization's rules
are written down once, versioned, and reviewed like code instead of living in
each person's head or in each prompt.

### Browser and GUI Agents, and RPA

When no interface exists, software can still use the screen. **Robotic process
automation (RPA)** replays a recorded or scripted sequence of clicks and
keystrokes. **Browser automation** frameworks drive a real browser through its
remote-control protocol, and are widely used for testing web applications —
the reference implementation itself was regression-tested this way. **AI
browser and computer-use agents** go further: they look at the screen, decide
what to do next, and operate the mouse and keyboard themselves. For classic SAP
GUI, SAP provides a scripting interface that can be enabled on the server.

These channels can reach anything a person can, which is their attraction. Their
contract is the screen, which changes with every release and was never designed
for software. They also run into the controls of the organization's own
endpoints; corporate security software that blocks a browser's
remote-control port is an everyday obstacle, not an edge case.

Two views of this channel are both true, and they answer the book's two
questions differently. As a way to *fill a gap* where no interface exists — an
unattended robot writing into the core through its screens — it is the last
resort, with a plan to retire it. As a way to *use the product's existing
functions* — an AI working the screens while a person watches, confirms, and
stays responsible for each write — it is the most direct way AI changes how a
packaged system is used, because it needs no integration project at all. The
chapter Agents at the Screen takes both seriously and draws the line between
them.

### How the Channels Relate

Read in this order, the tour shows one pattern. The newer channels mostly sit
on top of the older ones rather than beside them: an MCP tool wraps a released
interface, a Skill teaches an agent how to use the tools, a vendor agent calls
the vendor's own APIs. Only screen automation bypasses the interface layer, and
that is exactly what makes it the riskiest way to write. The chapter Principles:
Truth Lives in the Core turns this into a method for choosing between channels.

One more protocol completes the picture. Where MCP connects an agent to tools,
**A2A** (Agent2Agent) lets one agent delegate a task to another — for example,
an organization's own agent handing a finance question to a vendor's agent that
knows the product. A2A reached its first stable version in 2026 and is hosted by
the same foundation as MCP; SAP sits on its technical steering committee. For a
core system this matters because a request may arrive not from one agent but
from a chain of them, and each link raises again the question of on whose behalf
it acts. The chapter The Platform for Building and Running With AI returns to
both protocols.
